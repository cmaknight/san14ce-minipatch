# 데이터 파일 형식

패처가 읽고 다시 쓰는 게임 데이터 파일의 형식이다. 구현은 `patcher/lwc.py`(LWC 해제·압축)와 `patcher/s14.py`(.s14 코덱: 헤더 + LWC, fixdata 서명, DLC XOR)이고, 그룹(`patcher/groups/*`)은 코덱이 풀어 준 해제 데이터만 고친다. 값은 1.0.1 기준이다. 전체 구조는 [00-overview.md](00-overview.md).

## 1. 대상 파일

| 경로 | 내용 | 형식 | 쓰는 그룹 |
| --- | --- | --- | --- |
| `0010_xx/fixdataexce.s14` | 고정 데이터(진형, 개성 정의·설명문 등) | 평문 헤더 + LWC, **헤더 서명** | 2 개성, 5 진형 |
| `0010_xx/scedaexce*.s14` | 시나리오(새 게임이 개성 조건·효과를 여기서 읽는다) | 평문 헤더 + LWC | 2 개성 |
| `DLC/0010_xx/scedaexce*.s14` | DLC 시나리오 | 파일 전체를 XOR로 감싼 .s14 | 2 개성 |
| `0001_xx/msg*.bin` | 언어별 메시지(UI 문구·설명) | zp1 | 없음(참고) |

- 언어 폴더 접미사: `_KO`, `_JP`, `_SC`, `_TC`, `_EN`. EN에는 CE용 `fixdataexce`·`scedaexce`가 없다. 패처는 JP·KO·SC·TC만 다룬다.
- 파일명 접미사: 없음 = 무인판, `ex` = 파워업키트, `exce` = CE. 패처는 `exce`만 고친다.
- 개성 표·진형 레코드처럼 해제 데이터 안의 위치는 각 그룹 문서에 있다: [02-traits.md](02-traits.md), [05-formation.md](05-formation.md).

## 2. .s14 컨테이너

```
[평문 헤더]  u32 (0x66 등) + "SN14SCEXVER0001\0"(무인판 "SN14SCN_VER0001\0") + 제목·설명(UTF-16LE) + 기타
[LWC 블록]   §3
```

- 파일은 LWC 블록 끝에서 끝난다. 코덱은 블록 뒤에 바이트가 있으면 그대로 붙여 둔다(`trailer`).
- 헤더에 파일 크기·csize·usize·체크섬 필드는 없다. 예외는 fixdata의 헤더 서명(§4) 하나다.
- LWC 블록 시작 위치는 파일마다 다르다(CE fixdata·시나리오 0x2F2, 무인판 fixdata 0x1E0, EN은 또 다름). **고정값 대신 `LWC\x1A`를 검색해서 찾는다**(`lwc.find_block`).
- 헤더 4~8바이트가 `SN14`가 아니면 DLC XOR(§5)로 감싼 파일로 보고 먼저 푼다.

코덱(`S14`)의 저장 규칙:

1. 해제 데이터가 원본과 같으면 원본 바이트를 그대로 돌려준다.
2. 길이가 같으면 `lwc.repatch()`(최소 수정, §3.3), 길이가 바뀌면 `lwc.lwc()`(전체 압축, §3.4).
3. 만든 블록을 바로 다시 풀어 해제 데이터와 같은지 확인한다. 다르면 쓰지 않는다(`RuntimeError`).
4. 원본 헤더 서명이 맞던 파일(`signed`)만 새 서명을 쓴다(§4).
5. DLC 파일이면 원래 seed로 다시 감싼다(§5).

1.0.1 원본 fixdata:

| 파일 | 크기 | LWC 블록 | usize |
| --- | --- | --- | --- |
| `0010_JP/fixdataexce.s14` | 89,837 | 0x2F2 | 0x569AD |
| `0010_KO/fixdataexce.s14` | 81,527 | 0x2F2 | 0x59CBD |
| `0010_SC/fixdataexce.s14` | 89,340 | 0x2F2 | 0x59351 |
| `0010_TC/fixdataexce.s14` | 83,902 | 0x2F2 | 0x59351 |

## 3. LWC 압축 블록

옛 KOEI LS11 형식의 변형이다. 헤더는 리틀엔디언이다.

```
"LWC\x1A"
u32 usize        압축 해제 크기
u32 csize        비트스트림 바이트 수(사전 제외). 블록 끝 = 블록 시작 + 12 + 256 + csize
u8  dict[256]    0~255의 순열. 빈도순 심볼 표
u8  bits[csize]  MSB 우선 비트스트림
```

### 3.1 코드

`code()`는 가변 길이 정수 하나다. 값 v에 대해 n = floor(log2(v + 2))일 때 2n비트를 쓴다.

- 접두 n비트: 1이 n−1개 + 0 하나.
- 이어서 값 n비트.
- v = (2^n − 2) + (값 n비트). 즉 접두를 읽으며 쌓은 비트열(`11…10`)과 이어 읽은 n비트를 더한 값이다.

### 3.2 디코드

```
loop until len(out) == usize:
    c = code()
    if c < 256: out += dict[c]                    # 리터럴(사전 순위)
    else:       dist = c - 256; len = code() + 3  # LZ 역참조
                out[-dist]부터 len 바이트 복사(겹침 허용)
```

- 원본 fixdata는 비트스트림을 남김없이 정확히 다 쓴다(KO fixdataexce: 출력 367,805 B = usize, 비트 644,040 / 644,040).
- **게임 해제기 한도: 역참조 거리 ≤ 8,191, 일치 길이 ≤ 512.** 원본 스트림은 모든 파일에서 이 범위 안이다(거리 최대 8,190~8,191, 길이 최대 512, 코드 접두 최대 13비트). 범위를 넘는 블록은 게임이 DATA ERROR를 낸다. 8 KB 창을 쓰는 LS11과 같다.
- `lwc.tokens()`는 블록을 토큰 목록 `(출력 위치, 거리, 길이)`로 푼다. 리터럴은 거리 0·길이 1.

### 3.3 최소 수정 `repatch()`

해제 데이터 길이가 같을 때 쓴다(진형·개성은 모두 이 경우).

- 원본 블록을 토큰으로 풀고, 원본 사전과 토큰 구성을 유지한 채 다시 쓴다.
- 값이 바뀐 바이트는 리터럴로 쓴다. 역참조 중 복사 결과가 새 데이터와 어긋나는 구간만 리터럴로 쪼개고, 맞는 구간이 3바이트 이상이면 같은 거리의 역참조로 남긴다.
- 바꾼 것이 없으면 원본과 비트 단위로 같은 블록이 나온다(4개 언어 확인). 위 디코드 설명이 형식 전체를 빠짐없이 기술한다는 확인이기도 하다.
- 원본 토큰을 유지하므로 거리·길이 한도를 자동으로 지킨다.

### 3.4 전체 압축 `lwc()`

해제 데이터 길이가 바뀔 때만 쓴다.

- 사전: 해제 데이터의 바이트 빈도순 순열(같은 빈도는 바이트 값 순).
- 일치 탐색: 3바이트 해시 체인(후보 48개), 비트 이득(리터럴로 쓸 때 비트 − 역참조로 쓸 때 비트)이 가장 큰 후보, 1단계 지연 평가.
- 한도 `MAX_DIST = 8191`, `MAX_LEN = 512`. 이보다 큰 창·길이를 주면 `ValueError`. 테스트(`tests/test_lwc.py`)가 출력의 모든 역참조를 검사한다.
- 원본 압축기와 같은 바이트열을 만들지는 않는다. 해제 결과만 같다. 결정적이라 같은 입력이면 같은 출력이 나온다.

## 4. fixdata 헤더 서명

- 평문 헤더 오프셋 **463(0x1CF)** 의 u32 = `(해제 데이터 바이트 합 & 0xFFFF) ^ 5 mod 1071514531`.
- 게임은 `v ^ 35714969 mod 1071514531 == 바이트 합 & 0xFFFF`로 검사하고, 다르면 DATA ERROR를 낸다. 작은 RSA 형태다.
- 상수(`patcher/s14.py`): `SIG_OFF = 463`, `SIG_MOD = 1071514531`, `SIG_EXP = 5`, `SIG_CHECK_EXP = 35714969`. 모든 언어 공통.
- JP·KO·SC·TC의 `fixdata`·`fixdataex`·`fixdataexce` 12개 파일 모두 서명이 맞는다. EN은 헤더 구조가 달라 해당 없음.
- 시나리오(`sceda*`)는 같은 자리가 0이거나 맞지 않는다(전 언어 53개 × 4). 게임이 검사하지 않는 것으로 보고, 패처도 서명하지 않는다.
- 패처 규칙: 원본 서명이 맞는 파일만(`S14.signed`) 저장할 때 다시 서명하고, 쓴 직후 `signature_ok`로 확인한다. fixdata인데 원본 서명이 맞지 않으면 진형·개성 그룹이 "헤더 서명을 확인할 수 없어" 거부한다(서명 없이 값만 바꾸면 게임이 DATA ERROR를 낸다).
- 새 버전에서는 원본 fixdata에서 `signature_ok`가 참인지로 상수가 그대로인지 확인한다.

## 5. DLC 시나리오 XOR

DLC 시나리오(`DLC/0010_*/scedaexceNN.s14`)는 파일 전체가 XOR 키 스트림으로 감싸여 있다. 풀면 일반 시나리오와 같다(헤더 `SN14…` + LWC, 서명 없음).

```
s = seed
바이트마다: s = s * 1812433253 + 12345 (mod 2^32)
            out = in ^ ((s >> 16) & 0xFF) ^ ((s >> 24) & 0xFF)
seed = DLC_ID + 시나리오 번호
```

같은 함수(`s14.dlc_xor`)로 풀고 싼다.

### 5.1 DLC_ID 표

DLC_ID는 실행 파일 `.rdata`(평문)의 표에서 구한다.

- 위치: 문자열 `DLCFile::OpenToRead\0`이 끝난 곳을 8바이트로 올림 정렬한 곳.
- 항목: u32 배열, 항목 i = 시나리오 번호 − 9.
- 각 u32를 seed = 번호²로 위의 키 스트림과 XOR하면 DLC_ID다. 0이면 그 번호의 DLC 시나리오가 없다.

1.0.1 값(`patcher/s14.py` `DLC_SCENARIOS`, 시나리오 번호 → DLC_ID):

| 번호 | DLC_ID | 실제 seed |
| --- | --- | --- |
| 10 | 1198830 | 1198840 |
| 11 | 1198831 | — |
| 19 | 1258154 | — |
| 29 | 1431480 | — |
| 32 | 4598950 | 4598982 |
| 33 | 4598960 | 4598993 |

- 실제 seed는 JP·KO·SC·TC 모두 같다. 11·19·29는 해시 표에 원본 파일이 없어, 패처가 내용으로 판정한다([00-overview.md](00-overview.md) §6.2 `verify_unknown`).
- `DLC_IDS`에는 위 값과 함께 1198832(구판 시나리오 15)도 seed 후보로 들어 있다.

### 5.2 코덱 동작

- 헤더 4~8바이트가 `SN14`가 아니면 알려진 DLC_ID × 번호 1~255로 앞 8바이트를 풀어 `SN14`가 나오는 seed를 찾는다(`find_dlc_seed`). 못 찾으면 `ValueError`.
- 저장할 때 같은 seed로 다시 싼다.
- 해시를 모르는 DLC 시나리오는 파일 이름의 번호가 `DLC_SCENARIOS`에 있고 seed가 `DLC_ID + 번호`와 같아야 원본으로 본다.

## 6. zp1 (참고)

`0001_xx/msgdata*.bin`·`msggame*.bin`과 `0005` 폴더 항목의 컨테이너다. 패처는 이 파일을 고치지 않는다. DLL이 쓰는 메시지 번호를 확인할 때 쓴다.

```
"zp1\0", u32 total_size, u32 chunk_size(0x40000), u32 chunk_count, u32 chunk_comp_size[count]
0x800부터: 청크마다 [u32 len][zlib 스트림(78 DA)], 청크 시작은 0x80 정렬
```

### 6.1 msggame 문구 표와 메시지 번호

- 해제본: `u32 섹션 수(10)`, `(u32 오프셋, u32 크기) × 섹션`. 문구 섹션은 `u32 개수` + 섹션 기준 `u32 오프셋 × 개수` + 항목들. 섹션 6·8·9(17~18 B)는 문구 표가 아니다.
- **코드의 메시지 번호 = 섹션 × 10000 + 순번.** 메시지 빌더 0x1A23440의 vfunc+8(번호)과 0x30CF80(번호)이 같은 번호를 쓴다. 예: 0x349D(13469) = 섹션 1의 3469번 "의 발전Lv이 상승". KO `msggame_exce`는 22,525개.
- 항목은 바이트 모드로 시작한다. `07 07 01` 뒤는 UTF-16LE 글자, `07 07 02` 뒤는 바이트 제어 코드다.
  - `05 05 05`: 문구 끝. 무작위 대사처럼 한 항목에 여러 문구가 있으면 여러 번 나온다.
  - `02 xx[yy]`: 자리표시자(예 `FR` 세력, `F3` 무장, `FT` 장소, `2`·`3` 숫자).
  - `1B xx`: 글자색(`CZ` 원래 색).
- 예: 0x2A30 `{FR}의 {F3}, 전사`, 0x2A34 `{F3}, {FT}에서 처형됨`(사망 처리 0x295AA0이 쓰는 사망 로그 문구).
