# 그룹 5. 진형 밸런스 조정 (`formation` / ini 없음(데이터만) / 소스 `patcher/groups/formation.py`)

대상은 SAN14CE_KO.exe 1.0.1(PE 타임스탬프 0x6A983C25)과 함께 배포되는 데이터 파일이다. 실행 파일 주소가 나오면 RVA다. 전체 구조와 패처 골격은 [00-overview.md](00-overview.md).

## 하는 일
- 원본 학익 방어 30 → 36, 봉시 방어 18 → 20. 봉시 공군 45는 그대로 둔다.
- 진형 수치는 세이브에 복사되지 않고 불러올 때 계산하므로 **진행 중 세이브에도** 다시 불러오면 반영된다("(새 게임 필요)" 없음).
- DLL 기능은 없다. 이전 버전 값(학익 40, 봉시 21)을 적용했던 경우에도 다시 적용하면 원본 기준으로 새로 생성된다.

## 구현 방식
- 진형 표는 `0010_{JP,KO,SC,TC}/fixdataexce.s14`의 LWC 해제 데이터 안 청크 11(21칸, 레코드 152 B = 0x98)이다. 실행 파일·`0000/*.bin`·시나리오·msg에는 없다.
- 패처는 고정 오프셋 대신 레코드의 9바이트 패턴(구분, 기동, 점령3, 점령5, 미상, 공군, 공성, 파성, 방어)을 해제 데이터에서 검색한다(`find_unique`, 정확히 한 번). 방어 = 패턴 시작 +8(이름 N 기준 N+0x76). 원래 값이 18/30인지 확인한 뒤 1바이트를 바꾼다. 아니면 거부.
- 저장은 그룹 2와 같은 코덱(`S14.to_bytes`): 길이가 같으므로 `lwc.repatch`로 원본 토큰을 유지하고 바뀐 바이트와 그 바이트를 복사하던 역참조만 리터럴로 쪼갠다. 헤더 463의 서명을 다시 계산한다. 원본 서명이 맞지 않으면 쓰기 전에 거부한다(DATA ERROR 방지). 형식은 [data-formats.md](data-formats.md) "LWC"·"fixdata 헤더 서명".
- 그룹 2와 같은 fixdata를 고치므로 엔진이 원본에서 그룹 id 순(2 → 5)으로 한 번에 합성한다([00-overview.md](00-overview.md) 패처 골격, [02-traits.md](02-traits.md)).
- `verify_unknown`이 없다. 해시를 모르는 fixdata는 쓰기 전에 거부한다.

## 데이터 수정 위치
오프셋은 LWC 해제 스트림 기준. KO 헤더 포함 이미지 오프셋은 +0x2F2.

| 파일 | 레코드/오프셋 | 원래값 → 새값 | 다시 찾는 근거 |
| --- | --- | --- | --- |
| `0010_{KO,SC,TC}/fixdataexce.s14` | 봉시 방어 0x2D5BF(구분 바이트 0x2D5B7, 이름 0x2D549) | 18 → 20 | 패턴 `BONGSI` = `01 14 6E B4 00 2D 0D 08 12`(1, 20, 110, 180, 0, 45, 13, 8, 18) |
| `0010_{KO,SC,TC}/fixdataexce.s14` | 학익 방어 0x2D787(구분 0x2D77F, 이름 0x2D711) | 30 → 36 | 패턴 `HAKIK` = `01 10 1E 3C 00 12 0C 0D 1E`(1, 16, 30, 60, 0, 18, 12, 13, 30) |
| `0010_JP/fixdataexce.s14` | 봉시 방어 0x2D581(구분 0x2D579), 학익 방어 0x2D749(구분 0x2D741) | 18 → 20, 30 → 36 | 위 패턴과 같음 |
| (참고) 봉시 공군 | KO·SC·TC 0x2D5BC, JP 0x2D57E(패턴 +5) | 45 그대로 | 고치지 않음 |
| fixdata 4개 헤더 | 평문 헤더 463(0x1CF) u32 | 원래 서명 → 새 바이트 합 서명 | `signature_ok`가 원본에서 참이어야 함 |

- 진형 표 시작(KO): 해제 0x2D419, 청크 헤더 `(11, 21)`. 번호는 1부터(어린 = 1, 봉시 2, 학익 5).
- 적용 결과(크기 +2~3 B)는 결정적이다. 같은 원본이면 항상 같은 파일이 나온다.

## 패치 지점
- 실행 파일 패치 없음(데이터만).

## 쓰는 게임 함수·구조
| RVA·오프셋 | 내용 | 다시 찾는 근거 |
| --- | --- | --- |
| 진형 레코드 N+0x00 | 이름 UTF-16LE("봉시", "학익") | 정렬 없이 검색. 이름 뒤에 "강화"가 붙은 것은 기술 레코드라 제외 |
| N+0x6E ~ N+0x76 | 구분(1 육상, 2 수상, 0 미사용), 기동, 점령3, 점령5, 미상(0), **공군**(+0x73), 공성, 파성, **방어**(+0x76) | 게임 화면의 진형 수치와 일치. 공군·방어는 값을 바꿔 출진 편성 화면에서 확인 |
| N+0x77 / N+0x79 | u16 미상(0) / u16×8 미상(전부 100, 지형 보정 추정) | 패턴에 쓰지 않음 |

## 새 버전에서 다시 맞추는 순서
1. 새 fixdataexce 4개의 크기·SHA-256을 확인하고 `patcher/versions.py` 원본 해시를 갱신한다.
2. 각 파일을 LWC로 해제해 봉시·학익 패턴을 검색하고 공군·방어 값을 본다. 각 파일에서 한 번씩 나오면 그대로 쓴다.
3. 패턴이 안 맞으면(진형 값이 바뀐 업데이트) 이름 "봉시"/"학익"을 UTF-16LE로 정렬 없이 검색하고, 이름 +0x6F부터 8바이트가 필드 순서와 맞는지 본다. 또는 청크 헤더 `(11, 21)`과 레코드 152 B로 찾는다.
4. 새 원본 값으로 `formation.py`의 `BONGSI`·`HAKIK`과 `EDITS`의 원래 값을 고친다.
5. 원본에서 `signature_ok`가 참인지 본다. 거짓이면 서명 방식이 바뀐 것이라 패처가 거부한다. [data-formats.md](data-formats.md)의 서명 절차부터 다시 본다.
6. 해제 자체가 안 되면 `LWC\x1A` 헤더와 사전(256 B)부터 확인한다([data-formats.md](data-formats.md)).
7. 적용 결과 해시를 기록하고, 게임 출진 편성 화면에서 예상 방어가 비율대로 바뀌는지 본다.

## 검증
- 확인: 단위 테스트, 사본 적용·복원(원본 해시로 복귀). KO 게임 로드 정상(서명 갱신 파일).
- 출진 편성 화면 예상 수치 = 무장 계수 × 진형 수치(조조, 기존 세이브): 봉시 방어 443 → 492(×20/18). 학익 방어를 30 → 40으로 넣었을 때 738 → 984로 비율이 맞았다. 기존 세이브에도 반영된다.
- 현재 값(학익 36, 봉시 20) 게임에서 확인. 원본 복구 뒤 fixdataexce 4개가 원본과 같다.
- 미확인: 전투 피해 결과, JP/SC/TC 실행 파일로 게임 확인(KO만), 진형 공군 45 상한이 걸리는 위치(코드 상수인지, 표시만인지, 전투에도 걸리는지).

## 함정·결정
- 봉시 공군을 45보다 크게(48) 하면 편성 화면에 반영되지 않는다(공군을 내리거나 45 이하로 올리면 반영). 진형 공군이 45에서 잘린다고 보고 수정 대상에서 뺐다. `formation.py`의 `ATK = 5`는 쓰지 않는 상수다.
- 메모리의 진형 표를 고쳐도 편성 화면은 그대로다. 불러올 때 만든 값을 쓰므로 파일을 고친다.
- 값을 바꾼 fixdata는 헤더 서명이 맞지 않으면 DATA ERROR가 난다. 재압축도 역참조 한도(거리 ≤ 8,191, 길이 ≤ 512)를 지켜야 한다. 그래서 최소 수정 `repatch` + 서명 갱신을 쓴다.
- 언어마다 오프셋이 달라(JP가 0x3E 앞) 고정 오프셋 대신 패턴 검색을 쓴다.
- PK·무인판 `fixdataex.s14`·`fixdata.s14`는 CE 실행 파일이 읽지 않아 대상이 아니다(학익이 PK 값).
- 해제 0x3A9xx의 "봉시진형강화" 등은 기술 레코드다. 진형 수치가 아니다.
